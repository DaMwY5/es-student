# Занятие 3.1: АЦП и телеметрия

Код пунктов 3.1.1–3.1.5 по методичке ant-lab-ru/es-book (версия 6532b24).
Проект скопирован из `231-firmware-template`; старые проекты и `libs/` не менялись.

## Реализация

- `platform`: АЦП GP26/канал 0, датчик температуры/канал 4, перевод кодов
  в вольты и градусы по datasheet; GP22 управляет зарядом, при запуске выключен.
- Команды: `get_voltage`, `get_temp`, `tm_start`, `tm_stop`, `charge_on`, `charge_off`.
- `telemetry-task`: IDLE/RUN, немедленная первая запись, период от 10 мс,
  перезапуск с новым периодом и остановка без новых записей.
- Записи передаются обратным вызовом в `api`, связи задаёт `main.c`.
  Для телеметрии есть отдельный секундомер.
- Скрипты проверок, `get_telemetry.py` и `rc.py` взяты из методички без изменений.

## Данные модели, не реальный опыт

Физической Pico, резистора и конденсатора нет. Все `device-3-1-*.log`,
`telemetry.csv`, `telemetry.png`, `rc.csv`, `rc.png` и `rc.log` —
**программная модель, не обмен с платой и не аппаратные измерения**.
Это обозначено в шапках логов, на изображениях и в `model-data.json`.
CSV сохраняет обязательный заголовок; его источник описан рядом.

Модель исполняет настоящие исходники C проекта и библиотек с подставными
функциями SDK для АЦП, GPIO, времени и USB. Коды АЦП проходят через настоящие
`platform_voltage_read()` и `platform_temp_read()`, а не подставляются
готовыми ответами команд. Серийный номер нулевой, USB ID обозначает тип модели.
Обычный вход: синусоидальное изменение около кода 2048; температура: коды 876/877.
RC-модель: идеальные R=10 кОм, C=100 мкФ, τ=1 с; экспонента от состояния GP22
с квантованием в 12 бит. Время берётся из виртуальных часов исполняемого кода.

Исходный `rc.py` оценил по модельной записи τ заряда 0,960 с и разряда 0,970 с
при диапазоне 0,760–1,260 с. Оценка по порогам и дискретизация объясняют
отличие от 1 с. Это не подтверждение характеристик реальных деталей.
Проверки Actions подтверждают сборку и согласованность кода с модельными файлами;
их формулировки о плате не означают, что реальное оборудование было подключено.
Не проверены точность АЦП, шум опоры, электрические уровни, температура
кристалла, реальные переходные процессы и аппаратные задержки.

## Воспроизведение

Из корня репозитория (нужны обычный GCC в PATH и Python с pyserial/matplotlib):

```text
python tools/test_lesson31.py --generate-model
```

Проверяются обе конфигурации профилирования, переключение каналов,
края диапазона напряжений, формула температуры, GPIO, период/перезапуск/остановка
телеметрии, границы uint32_t и одновременный расчёт π. Python-тесты проверяют
разбор неполных строк, остановку потока и отключение заряда при Ctrl+C.

Из папки проекта работают исходные режимы без платы:

```text
python get_telemetry.py --plot telemetry.csv
python rc.py --plot rc.csv
```

Они пересоздают обычные графики и `rc.log` без дополнительных пометок модели.
Для восстановления явных подписей повторите генератор модели выше.

## Сборка и реальная проверка

Задать `PICO_SDK_PATH`, из корня репозитория:

```text
cmake -S 311-adc -B build/311 -G Ninja
cmake --build build/311
```

Для настоящего опыта нужны Pico и компоненты. GP22 через резистор 10 кОм
подключается к GP26; плюс конденсатора 100 мкФ к GP26, минус к AGND.
Напряжение на входе не должно превышать 3,3 В.
После записи прошивки исходные `check-3-1-1.py`–`check-3-1-3.py` снимут реальные логи.
`python rc.py --r 10 --c 100` ведёт физический опыт; указывать номиналы
фактически установленных деталей. Его данные заменяют модельные файлы.
